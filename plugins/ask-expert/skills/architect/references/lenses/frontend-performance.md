# 성능과 저사양 환경

첫 표시, 입력 반응, 화면 밀림을 저사양 기기와 느린 망에서도 지킬 구조를 정한다.

## 코드에서 먼저 확인할 것
- 측정값의 출처: 실제 사용자 데이터(RUM)가 있는지, 실험실 측정뿐인지. 어느 기기·망 분포를 기준으로 삼는지.
- 가장 큰 첫 화면 요소가 무엇이고, JS 번들이나 클라이언트 조회를 기다려야 나타나는지.
- 입력 직후 동기로 도는 무거운 계산, 큰 리렌더, 긴 작업(long task).
- 크기가 예약되지 않은 이미지·광고·스켈레톤·늦게 끼어드는 배너, 웹폰트 교체.
- 오래 켜 두는 화면(SPA, 웹뷰)에서 해제되지 않는 리스너, 무한히 크는 캐시.

## 판단 기준
- **첫 표시:** 첫 화면의 가장 큰 요소가 JS나 클라이언트 조회 뒤에 나오면 서버 HTML에 바로 넣고 우선순위를 올린다. 이미 HTML에 있으면 이미지 형식·크기·응답 시간을 본다. 지키는 것: 첫 표시 속도.
- **입력 반응:** 입력 직후의 계산이 무거우면 급하지 않은 갱신을 뒤로 미루고(전환 표시, 작업 양보), 계속 무거우면 워커로 옮긴다. 리렌더가 원인이면 상태 위치부터 고친다. 지키는 것: 상호작용 지연.
- **화면 밀림:** 늦게 채워지는 영역은 크기를 미리 예약하고, 위에 끼어드는 요소는 사용자 조작에 대한 응답으로만 넣는다. 지키는 것: 시각 안정성.
- **코드 분할:** 첫 화면에 쓰지 않는 무거운 부분이면 나눠서 늦게 불러오고, 대부분 사용자가 곧 쓰는 부분이면 같이 보낸다. 지키는 것: 첫 로드 대비 다음 동작 지연.
- **최적화 순서:** 실제 사용자 데이터에서 나쁜 지표와 나쁜 페이지를 먼저 고른다. 측정 없이 고치는 것은 가설로 다룬다. 지키는 것: 노력 대비 효과.

## 과설계 신호
- 문제가 측정되지 않았는데 수동 메모이제이션을 곳곳에 넣는다.
- 작업이 가벼운데 워커 분리나 자체 스케줄러를 만든다.

## 지킬 장치
- 라우트별 번들 크기 예산과 성능 점수 하한을 CI에서 검사한다.
- 실제 사용자 지표를 수집해 백분위 기준으로 경보를 건다.
