# 툴체인과 개발 경로

빌드·저장소 구조, 아키텍처 규칙을 자동으로 지키는 검사(fitness function), 모의 API와 테스트 기반, 팀이 따라가기 쉬운 기본 경로(Golden Path)를 정한다.

## 코드에서 먼저 확인할 것
- 문서에만 있고 CI에서 실패를 일으키지 않는 아키텍처 규칙. 그 규칙이 이미 깨진 곳.
- 검사 단계와 걸리는 시간: lint, 타입 검사, 단위·컴포넌트 테스트, E2E, 빌드. 로컬에서 한 번에 돌릴 명령이 있는지.
- 모의 API 핸들러를 개발 서버, 브라우저, 단위 테스트, E2E가 같이 쓰는지, 따로 만드는지. 등록되지 않은 네트워크 호출을 테스트가 막는지.
- 저장소가 하나의 패키지인지 여러 패키지(모노레포)인지, 나눈 이유가 배포 주기 차이인지.
- 새 기능을 만들 때 복사해 시작하는 틀(템플릿, 생성기, 예시 모듈)이 있는지.

## 판단 기준
- **규칙을 어디에 둘지:** 기계가 판정할 수 있는 규칙(import 방향, 금지 API, 원시값)이면 lint나 의존 규칙으로 CI에서 막고, 판단이 필요한 규칙만 리뷰와 문서에 둔다. 지키는 것: 규칙이 시간이 지나도 지켜짐.
- **어떤 수준의 테스트로 지킬지:** 화면 동작이면 렌더 결과와 역할 기준의 컴포넌트 테스트, 라우팅·SSR·핵심 흐름이면 E2E, 순수 계산이면 단위 테스트. 같은 것을 여러 층에서 겹쳐 검사하지 않는다. 지키는 것: 신뢰도 대비 실행 시간.
- **모의 API:** 백엔드보다 프론트가 먼저 움직이거나 E2E가 외부 서버에 흔들리면 핸들러 하나를 모든 환경에서 재사용한다. 백엔드가 안정적이고 계약 테스트가 있으면 범위를 좁힌다. 지키는 것: 개발 속도, 테스트 안정성.
- **한 패키지인가 여러 패키지인가:** 배포 주기와 소유 팀이 같으면 한 패키지 안에서 폴더 경계와 의존 규칙으로 나누고, 배포 주기나 소비자가 실제로 다르면 패키지를 나눈다. 지키는 것: 리팩터링 속도 대비 독립 배포.
- **기본 경로(Golden Path):** 같은 설정·보일러플레이트를 세 번째로 손으로 만들면 템플릿이나 생성기로 올린다. 지키는 것: 표준을 따르는 길이 가장 쉬운 길이 되는 것.

## 과설계 신호
- 팀이 하나이고 배포가 하나인데 모노레포 도구와 마이크로 프론트엔드를 검토한다.
- 커스텀 AST 규칙을 만들었는데 기존 lint 규칙 조합으로 충분하다.

## 지킬 장치
- 의존 방향과 금지 import를 검사하는 규칙을 CI 필수 단계로 둔다.
- 테스트 환경에서 등록되지 않은 요청을 오류로 처리한다(MSW `onUnhandledRequest: 'error'`).
- 로컬 한 줄 검증 명령(lint → 타입 → 테스트)을 두어 사람과 에이전트가 같은 순서로 확인한다.
