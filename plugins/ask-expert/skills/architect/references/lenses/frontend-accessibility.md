# 접근성

키보드와 스크린 리더만으로 핵심 사용자 여정을 마칠 수 있게 하는 구조와, 그것을 공통 부품의 계약으로 굳히는 방법을 정한다.

## 코드에서 먼저 확인할 것
- 핵심 여정(가입, 결제, 작성 등)을 키보드만으로 끝낼 수 있는지. 포커스 순서와 포커스가 갇히는 곳.
- 시맨틱 요소(`button`, `a`, `label`, 제목 단계)를 쓰는지, `div`에 클릭만 붙였는지.
- 대화상자·메뉴·탭 같은 복합 부품의 역할(role), 상태(aria-*), 열고 닫을 때 포커스 이동.
- 동적으로 바뀌는 내용(오류, 로딩 완료, 토스트)을 스크린 리더에 알리는 방법.
- 테스트가 요소를 역할과 이름으로 찾는지, 클래스나 test id로 찾는지.

## 판단 기준
- **어디서 보장할지:** 같은 패턴이 여러 화면에 나오면 공통 부품이 접근성을 책임지고 화면은 이름(레이블)만 넘기게 한다. 한 화면에만 나오면 그 화면에서 처리한다. 지키는 것: 일관성, 누락 방지.
- **네이티브 요소인가 ARIA인가:** 맞는 네이티브 요소가 있으면 그것을 쓰고, 없을 때만 ARIA 패턴을 그대로 따른다. 지키는 것: 보조 기술 호환.
- **포커스 관리:** 내용이 바뀌는 곳(라우트 이동, 대화상자 열고 닫기, 항목 삭제)마다 포커스가 갈 자리를 정한다. 지키는 것: 키보드 사용자의 위치 감각.
- **디자인과 부딪칠 때:** 시안이 대비, 터치 영역, 포커스 표시를 해치면 기준 충족을 우선하고 디자이너와 맞출 항목으로 올린다. 지키는 것: 법적·윤리적 최소선.

## 과설계 신호
- 기본 요소로 충분한 곳에 ARIA를 겹겹이 붙인다.
- 자동 검사 점수만 맞추고 키보드로 실제 여정을 걸어 보지 않는다.

## 지킬 장치
- 컴포넌트 테스트에서 역할과 접근 가능한 이름으로 요소를 찾는다. 못 찾으면 실패한다.
- 자동 접근성 검사(axe 등)를 E2E에 붙이되, 자동 검사가 못 보는 항목은 핵심 여정의 키보드 시나리오로 확인한다.
