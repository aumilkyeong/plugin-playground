# 실행 위치와 렌더링

어떤 코드를 서버·엣지·클라이언트 중 어디서 실행하고, 데이터를 언제 어디서 가져와 몇 겹으로 캐시할지 정한다.

## 코드에서 먼저 확인할 것
- 라우트마다 쓰는 렌더링 방식: 정적, 요청마다 서버 렌더링, 스트리밍, 클라이언트 전용. 라우트 파일과 `"use client"` 위치에서 본다.
- 클라이언트 경계의 크기: `"use client"`가 붙은 컴포넌트가 트리의 어느 높이에 있고, 그 아래로 얼마나 많은 코드가 딸려 가는지.
- 데이터 조회의 순서: 부모가 받은 뒤 자식이 받는 연쇄(폭포수)와 서버에서 차례로 기다리는 `await`. 조회 함수와 `Suspense` 경계에서 본다.
- 캐시 계층과 무효화: 요청 중복 제거, 서버 데이터 캐시, 라우트·CDN 캐시, 브라우저·라우터 캐시 가운데 무엇을 쓰고, 언제 무엇으로(태그, 경로, 시간) 비우는지.
- 서버에서 클라이언트로 넘기는 props: 직렬화되는 크기와, 비밀값이나 서버 전용 라이브러리가 섞여 넘어가는지.

## 판단 기준
- **서버에서 그릴지 클라이언트에서 그릴지:** 첫 화면에 필요하거나 검색·첫 표시 속도에 중요한 내용이면 서버에서, 사용자가 머무는 동안 자주 바뀌는 상호작용 영역이면 그 부분만 클라이언트로. 지키는 것: 첫 표시 속도, 내려받는 JS 양.
- **클라이언트 경계의 높이:** 상호작용이 잎 컴포넌트 몇 곳뿐이면 경계를 잎으로 내리고, 화면 전체가 하나의 상호작용 상태를 공유하면 그 상태를 가진 가장 낮은 공통 조상에 둔다. 지키는 것: 하이드레이션 비용.
- **폭포수:** 서로 기다릴 이유가 없는 조회면 병렬로 시작(동시 시작, 미리 불러오기)하고, 뒤 조회가 앞 결과를 입력으로 쓰면 연쇄를 유지하되 `Suspense` 경계를 나눠 먼저 준비된 부분부터 보낸다. 지키는 것: 첫 바이트·첫 표시 시간.
- **캐시 계층:** 사용자마다 다른 데이터면 공유 캐시(CDN, 라우트 캐시)에서 빼고, 모두에게 같고 바뀌는 시점이 분명하면 태그로 묶어 바뀔 때 비운다. 시간 기반 만료는 늦게 보여도 되는 데이터에만. 지키는 것: 일관성, 서버 부하.
- **엣지 실행:** 지역 지연이 실제로 문제이고 데이터 원천이 엣지 가까이 있으면 엣지, 데이터베이스가 한 지역에 있으면 그 지역 서버. 지키는 것: 응답 지연.

## 과설계 신호
- 트래픽과 지연 문제가 관측되지 않았는데 엣지 실행과 다계층 캐시를 먼저 설계한다.
- 라우트가 몇 개뿐인데 렌더링 방식을 라우트마다 다르게 섞는다.
- 무효화 규칙을 설명할 수 없는 캐시가 늘어난다.

## 지킬 장치
- 서버 전용 모듈에 `server-only`를 붙여 클라이언트 번들에 섞이면 빌드가 실패하게 한다.
- 라우트별 첫 화면 JS 크기 예산을 CI에서 검사한다.
- 핵심 라우트가 정적에서 동적으로 바뀌면 빌드 출력 비교로 잡는다.
