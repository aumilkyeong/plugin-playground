# 앱 웹뷰와 브릿지

네이티브 앱과 웹이 주고받는 계약(브릿지 API), 버전이 다른 앱과 웹이 함께 돌 때의 호환, 기능을 웹과 네이티브 중 어디에 둘지를 정한다.

## 코드에서 먼저 확인할 것
- 브릿지 호출이 한 곳(SDK, 어댑터)으로 모였는지, 화면 코드가 `postMessage`나 전역 객체를 직접 부르는지.
- 요청과 응답의 짝 맞추기, 시간 초과, 오류 형식, 타입 정의가 있는지.
- 앱 버전과 웹 버전이 어긋날 때의 처리: 기능 존재 여부를 묻는지(기능 탐지), User-Agent로 추측하는지.
- 같은 웹 코드가 일반 브라우저에서도 도는지, 브릿지가 없을 때의 대체 동작.
- 네이티브 생명주기 연동: 뒤로 가기 제스처, 백그라운드 전환, 딥링크, 토큰 갱신.

## 판단 기준
- **기능을 어디에 둘지:** 자주 바뀌고 빠른 배포와 실험이 필요하거나 웹에서도 제공해야 하는 화면은 웹에, 기기 하드웨어·백그라운드 실행·푸시 수신·고프레임 제스처·오프라인 즉시 실행이 필요한 기능은 네이티브에. 지키는 것: 배포 속도 대비 기기 기능.
- **계약의 모양:** 호출이 몇 개면 타입이 붙은 함수 목록으로 평평하게, 영역별로 수십 개가 되면 그때 이름 공간으로 묶는다. 계약은 한 곳에 정의하고 앱과 웹이 같은 정의를 본다. 지키는 것: 단순성, 진화 가능성.
- **버전 호환:** 앱 업데이트를 강제할 수 없으면 웹이 기능 탐지로 분기하고, 없을 때의 대체 동작을 정한다. 강제 업데이트가 가능하면 최소 지원 버전을 둔다. 지키는 것: 구버전 사용자 경험.
- **신뢰 경계:** 웹에서 오는 호출은 네이티브가 출처(허용 도메인)와 권한을 검증하고, 민감한 기능은 웹이 아니라 네이티브가 최종 판단한다. 지키는 것: 기기 권한 보호.

## 과설계 신호
- 브릿지 호출이 몇 개인데 범용 RPC 프레임워크와 스키마 레지스트리를 만든다.
- 실제로 어긋나는 버전 조합이 없는데 모든 호출에 버전 협상을 붙인다.

## 지킬 장치
- 화면 코드에서 전역 브릿지 객체·`postMessage` 직접 사용을 lint로 막고 SDK만 허용한다.
- 브릿지가 없는 환경(일반 브라우저)과 구버전 응답을 흉내 낸 모의 브릿지로 테스트한다.
