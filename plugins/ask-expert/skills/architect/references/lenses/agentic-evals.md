# 평가(eval)와 관측

비결정적인 LLM 기능이 계속 기준을 지키는지 무엇으로 확인하고, 실제 실행에서 무엇을 기록할지 정한다.

## 코드에서 먼저 확인할 것
- 대표 입력과 기대 결과를 모은 eval 세트가 있는가, 실패 사례가 그 세트로 들어가는가
- 코드로 검사할 수 있는 부분(스키마, 테스트 통과, 파일 존재)과 판단이 필요한 부분
- 프롬프트·모델·도구를 바꿀 때 eval이 도는가
- 실행 기록에 턴 수, 도구 호출, 토큰, 지연, 오류가 남는가

## 판단 기준
- **채점 방식:** 코드로 확인할 수 있으면 코드 검사(스키마, 테스트, 정규식). 판단이 필요하면 LLM 채점을 쓰되 통과/실패 체크리스트로 쪼개고, 가끔 사람 판정과 맞춰 본다. 지키는 것: 재현성
- **결과 대 경로:** 기본은 최종 결과(테스트 통과, 산출물)로 채점한다. 경로는 여럿일 수 있으니 도구 순서는 비용 지표(턴 수, 토큰)로만 보고, 금지 경로(위험 도구, 범위 밖 파일)만 경로로 채점한다
- **반복:** 결과가 매번 달라지므로 케이스마다 여러 번 돌려 통과율로 본다
- **eval을 둘 때:** 프롬프트를 고칠 때마다 손으로 확인하고 있다면 그 확인을 eval 케이스로 옮긴다
- **관측:** 실행마다 트레이스(입력, 도구 호출, 출력, 토큰, 지연)를 남겨 실패를 재현 가능한 케이스로 바꾼다

## 과설계 신호
- 케이스가 몇 개 없는데 채점 모델 보정 파이프라인부터 만든다
- 코드로 검사할 수 있는 것을 LLM 채점에 맡긴다
- 사용자가 거의 없는데 운영 샘플링 평가를 먼저 붙인다

## 지킬 장치
- CI에서 eval 통과율 하한과 비용 상한을 검사한다
- 운영에서 난 실패를 eval 케이스로 옮기는 절차를 둔다
