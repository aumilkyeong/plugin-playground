# 데이터 일관성과 시스템 간 통합

데이터를 어디에 저장하고, 여러 저장소·서비스 사이의 일관성과 실패를 어떻게 다루고, 시스템끼리 어떤 계약으로 주고받을지 정한다.

## 코드에서 먼저 확인할 것
- 사용자 동작 하나가 몇 개의 저장소·서비스를 바꾸는가
- 같은 요청이 두 번 오면 어떻게 되는가: 재시도, 중복 클릭, 메시지 재전달
- 읽기와 쓰기의 비율, 읽는 모양(목록, 검색, 집계)이 쓰는 모양과 다른가
- 캐시가 있다면 원본이 바뀔 때의 무효화 경로
- 다른 팀·앱과 주고받는 API·이벤트 스키마와 버전 규칙

## 판단 기준
- **일관성 수준:** 금액, 재고, 권한처럼 틀리면 되돌리기 어려운 값은 한 저장소의 트랜잭션 안에 둔다. 피드, 카운트, 알림처럼 잠시 늦어도 되는 값은 결과적 일관성. 지키는 것: 정확성 대 가용성
- **여러 저장소에 걸친 변경:** 되도록 한 저장소로 모은다. 나눠야 하면 2PC 대신 saga(단계별 보상)와 outbox(쓰기와 이벤트 발행을 한 트랜잭션에)
- **멱등성:** 재시도될 수 있는 쓰기는 모두 멱등 키를 받는다
- **저장소 선택:** 관계와 트랜잭션이 중요하면 관계형 DB가 기본. 다른 저장소는 그 접근 패턴이 측정으로 문제일 때 고른다
- **읽기 모델 분리(CQRS):** 읽는 모양이 쓰는 모양과 크게 다르고 읽기가 압도적일 때 쓴다. 그 밖에는 모델 하나
- **계약:** 외부와 주고받는 스키마는 하위 호환 규칙(필드는 추가만, 제거는 단계적으로)과 버전을 정한다. 지키는 것: 독립 배포
- **캐시:** 원본의 주인과 무효화 시점을 먼저 정하고 캐시를 둔다. 무효화를 정할 수 없으면 만료 시간과 허용하는 오래됨을 명시한다

## 과설계 신호
- 팀 하나, 저장소 하나로 될 일을 마이크로서비스와 메시지 브로커로 나눈다
- 요구 없이 이벤트 소싱이나 CQRS를 도입한다
- 측정 없이 캐시 계층을 여러 겹 둔다

## 지킬 장치
- 계약 테스트: 소비자가 기대하는 스키마로 제공자 변경을 검사한다
- 멱등성 테스트: 같은 요청 두 번에 결과 하나
- 의존 규칙: 모듈은 다른 모듈의 데이터를 그 모듈의 공개 API로만 읽는다(정적 검사)
