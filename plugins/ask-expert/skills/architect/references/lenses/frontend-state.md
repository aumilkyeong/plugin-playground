# 상태의 자리와 모듈 경계

각 상태의 원천(SSOT)을 서버 캐시·URL·컴포넌트 로컬·영속 저장소 중 어디에 둘지, 그리고 기능 모듈 사이의 의존과 공통화를 정한다.

## 코드에서 먼저 확인할 것
- 상태의 종류별 현재 위치: 서버에서 온 데이터, 공유되어야 하는 화면 조건(검색어, 필터, 탭), 잠깐 쓰는 UI 상태가 각각 어디 저장되는지. 전역 스토어에 성격이 다른 상태가 섞였는지.
- 같은 데이터의 사본: 하나의 값이 두 곳 이상에 저장되어 서로 맞춰야 하는 곳.
- 모듈 의존 방향: 공통(`shared`) → 기능(`features`) → 화면 조합(`app`)으로 한 방향인지, 기능끼리 내부 파일을 직접 가져다 쓰는지.
- API 응답 타입의 출처: 명세에서 생성하는지, 손으로 쓰는지. 응답 모양을 화면에 맞게 바꾸는 곳이 컴포넌트 안인지 별도 계층인지.

## 판단 기준
- **서버 데이터 조회:** 첫 화면에 필요한 데이터면 서버 컴포넌트에서 조회하고, 머무는 동안 폴링·무한 스크롤·낙관적 갱신·여러 컴포넌트의 캐시 공유가 필요하면 클라이언트 쿼리 라이브러리로. 지키는 것: 번들 크기, 신선도.
- **URL인가 메모리인가:** URL을 복사해 보낸 사람이 같은 화면을 봐야 하는 상태면 URL이 원천이다. 열린 드롭다운, 제출 전 입력값처럼 공유와 무관하면 컴포넌트 상태. 뒤로 가기로 되돌아가야 하면 `push`, 아니면 `replace`. 지키는 것: 공유 가능성, 새로고침 복원.
- **값을 저장할지 계산할지:** 다른 값에서 계산할 수 있으면 저장하지 않고 그릴 때 계산한다. 원천이 둘이 되는 순간 어긋날 곳이 생긴다. 지키는 것: 일관성.
- **복잡한 상태 전이:** 상태 조합 중 불가능한 것이 있으면 리듀서나 상태 머신으로 모델링해 그 조합을 타입에서 없앤다. 지키는 것: 정확성.
- **공통화:** 도메인 지식이 없는 UI 기본 부품과 범용 유틸만 `shared`로 올리고, 도메인 맥락이 담긴 컴포넌트는 비슷해 보여도 각 기능 안에 둔다. 세 번째로 같은 요구가 나올 때 다시 본다. 지키는 것: 변경 격리.
- **오프라인에서 써야 하는 기능:** 끊겨도 동작해야 하면 로컬 영속 저장소와 보낼 일 대기열(outbox)을 두고, 아니면 온라인 전제로 단순하게. 지키는 것: 신뢰성 대비 복잡도.

## 과설계 신호
- 상태가 몇 개뿐인데 전역 스토어 라이브러리를 들인다.
- 한 곳에서만 쓰는 컴포넌트를 미리 `shared`로 올린다.
- 오프라인 요구가 없는데 동기화 엔진이나 CRDT를 검토한다.

## 지킬 장치
- 의존 방향 규칙(dependency-cruiser, ESLint import 규칙)으로 역방향 import와 기능 간 내부 참조를 막는다.
- API 명세에서 타입을 생성하고, 생성 결과가 최신인지 CI에서 검사한다.
