# 모델 고르기와 비용·지연

작업마다 어떤 모델을 쓸지, 캐싱·병렬 실행으로 지연과 비용을 어떻게 줄일지 정한다.

## 코드에서 먼저 확인할 것
- 요청 하나가 내부에서 LLM을 몇 번 부르는가
- 호출마다 바뀌지 않는 앞부분(시스템 프롬프트, 도구 정의)과 바뀌는 부분의 순서
- 서로 독립인 호출을 순서대로 기다리는가
- 장애(요청 한도, 서버 오류) 때 재시도·대체 경로가 있는가
- 작업 하나당 비용과 지연을 재고 있는가

## 판단 기준
- **모델 단계:** 계획, 모호한 추론, 최종 종합은 가장 강한 모델. 정형 변환, 탐색, 요약은 빠른 모델. 분류, 라우팅, 필터는 가장 작은 모델. 낮추기 전에 품질 차이를 eval로 확인한다. 지키는 것: 비용, 지연
- **라우팅 도입:** 요청 유형이 섞여 있고 쉬운 요청이 많을 때 분류기를 앞에 둔다. 유형이 하나면 모델 하나
- **캐싱:** 고정 부분을 메시지 앞에 두고, 시각·임시 상태처럼 매번 바뀌는 값은 뒤쪽에 둬서 프롬프트 캐시 적중을 높인다
- **병렬:** 독립 호출(파일 읽기, 검색, 하위 작업)은 한 턴에 함께 보낸다
- **자체 호스팅 대 API:** 데이터가 밖으로 나갈 수 없거나, 단순 반복 작업이 대량이라 비용 차이가 측정으로 입증될 때 자체 호스팅. 그 밖에는 API

## 과설계 신호
- 트래픽이 작은데 의미 기반 라우터와 여러 제공처 장애 전환을 먼저 만든다
- 비용을 재기 전에 모델을 낮춘다
- 측정 없이 자체 호스팅을 계획한다

## 지킬 장치
- 작업당 토큰·비용·지연 예산을 CI eval에서 검사한다
- 캐시 적중률을 로그로 남기고 떨어지면 알린다
