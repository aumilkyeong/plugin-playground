# 신뢰성과 관측

일부가 실패해도 화면 전체가 무너지지 않게 하는 격리 단위, 불안정한 망과 오프라인에서의 동작, 실제 사용자 환경에서 문제를 보는 방법을 정한다.

## 코드에서 먼저 확인할 것
- 오류 경계(ErrorBoundary, 라우트 오류 화면)가 어느 높이에 있는지. 한 위젯의 오류가 페이지 전체를 하얗게 만드는 경로.
- 요청 실패 처리: 재시도 횟수와 간격, 시간 초과, 사용자에게 보이는 상태(빈 상태, 다시 시도 버튼).
- 실제 사용자 환경의 오류와 성능을 수집하는지, 클라이언트 요청과 서버 로그를 같은 추적 ID로 잇는지.
- 오프라인·끊김 처리: 끊겼을 때 사용자가 한 입력이 어디로 가는지.

## 판단 기준
- **격리 단위:** 실패해도 나머지 화면이 쓸모 있는 영역(추천, 부가 위젯)은 그 영역에 경계를 두고, 실패하면 화면 자체가 의미 없는 영역(본문 데이터)은 라우트 수준 경계로 처리한다. 지키는 것: 부분 장애 격리.
- **재시도:** 다시 보내도 안전한 요청(조회, 멱등 요청)만 자동 재시도하고 간격을 점점 늘린다. 부작용이 있는 요청은 사용자 확인 뒤 재시도하거나 멱등 키를 붙인다. 지키는 것: 정확성, 서버 보호.
- **끊김 대응:** 끊겨도 입력을 잃으면 안 되는 기능이면 로컬에 쌓았다가 연결되면 보내고, 그렇지 않으면 끊김을 알리고 다시 시도하게 한다. 지키는 것: 데이터 보존 대비 복잡도.
- **관측 범위:** 사용자 수가 작으면 오류 수집과 핵심 지표부터, 서비스 사이 지연 원인을 추적해야 하면 분산 추적까지. 지키는 것: 원인 파악 시간.

## 과설계 신호
- 서비스가 하나인데 분산 추적 파이프라인부터 만든다.
- 모든 컴포넌트에 오류 경계를 씌워 실패가 조용히 숨는다.

## 지킬 장치
- 주요 영역의 오류 경계 폴백이 그려지는지 확인하는 컴포넌트 테스트(일부러 던지는 오류).
- 실제 사용자 오류율과 실패 요청 비율에 경보를 건다.
