# 에이전트 구조와 실행 루프

LLM 기능을 고정된 코드 흐름으로 짤지, 스스로 도구를 고르는 에이전트로 짤지, 에이전트를 몇 개로 나눌지 정한다.

## 코드에서 먼저 확인할 것
- 작업 단계와 순서가 미리 정해지는가: 호출 흐름, 프롬프트 체인, 분기 코드
- 실행 중 중간 결과(검색 결과, 오류 내용)를 보고 다음 행동을 바꿔야 하는가
- 한 번 실행이 얼마나 걸리고, 중간에 끊기면 어디서부터 다시 하는가: 상태 저장, 재시도 코드
- 하위 작업이 서로 독립인가, 뒤 작업이 앞 결과를 쓰는가
- 종료 조건과 단계·토큰 상한이 코드에 있는가

## 판단 기준
- **코드 흐름 대 에이전트:** 입력·출력 규칙이 분명하거나 순서가 바뀌면 안 되는 일이면 고정 흐름(체인, 라우팅, 병렬)을 짜고 노드마다 LLM을 부른다. 단계 수와 도구 순서를 실행 중 결과를 보고 정해야 하면 에이전트 루프. 지키는 것: 예측 가능성, 속도, 디버깅
- **단일 대 다중 에이전트:** 도구와 필요할 때 읽는 지침(skill)만으로 풀리면 단일 에이전트. 하위 작업이 메인 컨텍스트를 덮을 만큼 크거나, 독립인 관점을 동시에 봐야 하거나, 쓰는 쪽과 검증하는 쪽의 권한·시각을 떼야 할 때 나눈다. 지키는 것: 맥락 일관성, 비용
- **나누는 모양:** 하위 작업이 독립이면 조율자가 맡기고 종합하는 orchestrator-workers. 결과를 계속 주고받아야 하는 작업은 한 에이전트에 둔다. 에이전트끼리 대화가 늘수록 비용과 오류 전파가 커진다
- **생성과 검증:** 품질 기준을 글로 적을 수 있으면 생성기와 평가기를 나눈 evaluator-optimizer 루프. 적을 수 없으면 사람 검토
- **긴 실행:** 외부 장애나 사람 승인 대기를 거치면 단계마다 상태를 저장하고 멱등하게 재개한다. 몇 초짜리면 실패 시 처음부터 다시 실행

## 과설계 신호
- 단계가 고정된 일을 에이전트 루프로 돌린다
- 에이전트 하나가 도구 몇 개로 할 일을 역할별 에이전트 여럿으로 나눴다
- 종료를 모델 판단에만 맡기고 상한이 코드에 없다

## 지킬 장치
- 루프마다 최대 단계·토큰 상한을 코드로 두고, 넘으면 실패로 기록한다
- 대표 작업 몇 개로 궤적 eval: 턴 수, 도구 호출 수가 기준을 넘으면 실패
