# ask-expert: 전문가 자문

구조나 기술 선택을 정해야 할 때, Claude가 전문가 역할의 보조 Claude(agent)에게 코드와 제약만 넘겨 자문을 받게 하는 플러그인이다. 보조 Claude는 지금까지의 대화를 모른다. 그래서 대화 중에 Claude가 이미 기운 답에 끌려가지 않고 판단한다. 답은 "권장: …"으로 시작하고, 정할 것을 Q1, Q2로 나눠 번호마다 선택지 a, b와 권장안을 붙여 돌아온다. 그래서 "모두 권장안을 따름"이나 "Q2만 a"처럼 한 줄로 고르면 된다. 지금 있는 전문가는 소프트웨어 아키텍트 하나다.

```bash
claude plugin marketplace add aumilkyeong/plugin-playground   # 처음 한 번, 마켓플레이스 'aumilkyeong' 등록
claude plugin install ask-expert@aumilkyeong
```

**상태 (2026-11-19):** eval(실제 모델에 같은 상황을 시켜 보고 채점하는 시험) 케이스 6개를 돌렸고, 한 케이스는 고친 뒤 다시 돌려 모두 통과했다. 실제 작업 세션에서 자문을 받아 본 적은 아직 없다([확인한 범위](#확인한-범위)). 이 저장소 주인이 2026-12-15까지 4주를 써 보고, 한 번도 발동하지 않았거나 권장안이 절반 넘게 뒤집혔으면 고치거나 마켓플레이스에서 뺀다. 설치 전에 써 보려면 [설치 없이 써 보기](#설치-없이-써-보기)를 본다.

설치한 뒤에는 평소처럼 물으면 된다. "목록 필터 상태를 어디에 두는 게 좋을지 검토해줘", "이 설계에서 내가 놓친 위험이 있을까?"처럼 트레이드오프(무엇을 얻고 무엇을 포기하는지), 대안, 구조, 놓친 위험을 물으면 skill(Claude가 필요할 때 꺼내 읽는 작업 지침)이 저절로 발동한다. 직접 부르려면 `/ask-expert:architect <질문>`을 입력한다.

묻지 않아도 Claude가 먼저 자문할 때가 있다. 구현하다가 나중에 되돌리기 어려운 결정을 혼자 내려야 할 때다. 데이터 저장 모양, 앱과 웹이나 서비스끼리 주고받을 규격(API), 프레임워크 선택 같은 것이다. 그러면 답 첫 줄에 자문했다고 알리고, 사용자가 고를 때까지 그 결정에 기대는 구현을 멈춘다. 이미 정해 준 결정이나 설계 문서에 적힌 결정은 따르고 묻지 않는다.

설치 전에 알아 둘 것이 둘 있다.

- **느리고 비싸다.** 아키텍트는 `opus`(그때그때 최신 Opus 모델을 가리키는 이름)에서, 생각하는 깊이(effort)를 다섯 단계 가운데 둘째로 높은 `xhigh`로 돌게 설정했다. 그래서 자문이 들어간 답은 평소 답보다 오래 걸리고, 구독 요금제면 사용 한도를, API 키면 비용을 그만큼 더 쓴다. eval에서 잰 값(API 요금으로 환산, 예제 저장소 기준)은 아래와 같다.

  | 질문 | 플러그인 켬 | 플러그인 끔 |
  |---|---|---|
  | 상태를 어디에 둘지 (보통 무게, 자문 1번) | 약 $0.9, 4~6분 | 약 $0.1, 30초 |
  | 결제 설계의 위험 찾기 (무거움, 자문 3번) | 약 $2.5, 5~7분 | 약 $0.1, 45초 |
  | 앱-웹 브릿지 구현 요청 (무거움, 자문과 반박) | 약 $2.7, 17분 | 약 $0.2, 1분 |

  Claude가 먼저 자문하는 것만 따로 끄는 설정은 없다. 그때그때 "자문 없이 진행해"라고 하거나, `claude plugin disable ask-expert@aumilkyeong`로 플러그인을 끈다. Claude를 Anthropic API가 아닌 클라우드(Amazon Bedrock, Google Cloud, Microsoft Foundry)로 쓰면 `opus`가 더 오래된 모델을 가리킬 수 있고, `xhigh`를 지원하지 않는 모델에서는 한 단계 낮은 `high`로 돈다.
- **이 저장소 주인의 기준이 함께 적용된다.** 결정마다 권장안을 붙이고, 기존 구현을 출발점으로 삼지 않고 백지에서 낸 대안을 함께 보이고, 지금 꼭 만들 것과 나중에 더할 것을 나누고, 정할 것과 위험을 초보자도 알 말로 다시 써서 번호를 붙여, 하나씩 차례로 검토할 수 있게 한다. 바꾸고 싶으면 [개인 기준](#개인-기준은-friction-loop가-키운다)을 본다.

## 답은 이런 모양으로 온다

아래는 형식을 보이려고 만든 예시다.

```text
권장: 필터와 정렬을 URL 쿼리에 둡니다. 상세에서 돌아와도, 새로고침해도, 주소를 보내도 같은 목록이 보입니다.

Q1. 고른 필터를 어디에 기억할까? (지금은 화면을 떠나면 사라지는 컴포넌트 상태에만 있음)
  a. 전역 store · 얻는 것: 코드 변경이 적음 / 포기하는 것: 새로고침과 주소 공유에서 사라짐
  b. URL 쿼리 · 얻는 것: 뒤로 가기·새로고침·공유에서 유지 / 포기하는 것: 주소가 길어지고 값 검증이 필요   ← 권장: 세 상황을 모두 지킴

다시 볼 조건: 필터가 열 개를 넘어 주소가 너무 길어지면 저장한 필터 목록으로 바꾼다.
```

## 자문 횟수는 결정을 되돌리는 비용에 맞춘다

자문이 비싸서, Claude가 결정의 무게를 먼저 정하고 그에 맞춰 부른다.

| 무게 | 예 | 하는 일 |
|---|---|---|
| 가벼움 | 스크립트·파일 이름, 파일 위치 | 아키텍트를 부르지 않고 Claude가 같은 형식으로 짧게 답한다 |
| 보통 | 컴포넌트 경계, 상태를 둘 곳, 공통 폴더로 올릴지 | 아키텍트에게 한 번 묻는다 |
| 무거움 | 데이터 모델, 앱·웹·서비스 사이에 주고받을 규격(API), 프레임워크 선택 | 한 번 묻고, 아키텍트 역할의 보조 Claude를 새로 하나 더 띄워 그 권장안을 반박하게 한다. 사용자가 정하면 ADR(결정과 이유를 남기는 짧은 문서)로 남길지 묻는다 |

이 횟수는 대안 가운데 하나를 고르는 질문의 경우다. 이미 정한 설계에서 놓친 위험을 찾는 질문은 한 번 부르고, 무거운 설계일 때만 성능, 접근성, 보안처럼 관점을 나눠 최대 3번 동시에 부른다. 사용자가 "이 구조면 해결될 것 같은데 검토해줘"처럼 자기 가설을 맡기면 처음부터 반박하는 쪽으로 묻는다.

## 아키텍트에게는 결론을 넘기지 않는다

먼저 본 답에 판단이 끌려가는 것을 앵커링(anchoring)이라 한다. Claude가 "URL에 두면 될 것 같은데 검토해줘"라고 물으면 아키텍트는 그 답을 맞다고 확인해 돌아오기 쉽다. 그래서 Claude는 사용자 질문 원문, 제약, 읽을 코드의 경로, 이미 내린 결정만 넘기고 자기가 기운 안은 넘기지 않는다. 아키텍트는 코드를 직접 읽고, 백지에서 낸 안을 하나 이상 포함해 대안을 비교한다. 돌아온 답에 인용된 파일과 사실은 Claude가 다시 열어 확인한 뒤 돌려준다.

## 설치 없이 써 보기

이 저장소를 내려받고, 내려받은 폴더에서 Claude Code를 연다. 플러그인은 설치되지 않고 이 세션에만 불러온다.

```bash
git clone https://github.com/aumilkyeong/plugin-playground.git
cd plugin-playground
claude --plugin-dir ./plugins/ask-expert
```

여기부터는 플러그인을 고치거나 전문가를 더하려는 사람을 위한 내용이다.

## 파일마다 하는 일

| 파일 | 역할 |
|---|---|
| `references/consult.md` | 모든 전문가가 따르는 공통 절차: 무게 정하기, 질문 꾸리기, 맡기기, 확인, 돌려주기 |
| `references/standards.md` | 개인 기준. 이 저장소 주인에게서 되풀이해 나온 자문 방식의 지시 |
| `skills/architect/SKILL.md` | 아키텍트 자문의 발동 조건, 결정·위험 찾기·반박 세 방식, 렌즈 고르기, ADR, Claude가 먼저 자문하는 경우 |
| `skills/architect/references/lenses/` | 렌즈. 분야마다 판단 기준, 과설계 신호, 결정이 지켜지는지 확인하는 lint 규칙·테스트의 예, 원문 링크를 담은 파일 19개와 색인. 아키텍트는 질문에 걸리는 렌즈 1~3개만 연다 |
| `skills/architect/references/adr-template.md` | 프로젝트에 ADR 형식이 없을 때 쓰는 틀 |
| `agents/architect-advisor.md` | 실제로 자문하는 아키텍트. 읽기 도구(Read, Grep, Glob)와 웹 검색만 쓰고 파일을 고치지 않는다 |
| `evals/` | eval 케이스 6개. 실행 방법은 [`evals/README.md`](evals/README.md)에 있다 |

전문가를 더하려면 `skills/<이름>/SKILL.md`와 `agents/<이름>-advisor.md` 두 파일을 만든다. 예를 들어 UX 전문가는 `/ask-expert:ux-designer`가 된다. 공통 절차와 개인 기준은 `references/`의 것을 함께 쓴다. agent 이름에 `-advisor`를 붙이는 이유는 skill과 agent가 같은 이름이면 Claude가 skill 안의 "이것을 부른다"를 skill과 agent 가운데 어느 쪽으로 읽을지 헷갈리기 때문이다.

## 개인 기준은 friction-loop가 키운다

`references/standards.md`의 네 기준은 이 저장소 주인의 2026-10-16~11-17 대화 기록에서 되풀이된 지시를 근거로 했다. 예를 들어 권장안 기준은 "권장안을 따름"이라는 답이 17개 프로젝트에서 197번 나와서 넣었다. 설치하면 이 기준이 그대로 적용된다.

내 기준으로 바꾸려면 이 저장소를 포크(내 계정으로 복사)하고, 포크한 사본에서 이 파일을 고친 뒤 그 사본을 설치한다. 사본을 설치하는 명령은 [루트 README의 '내 사본에서 주간 검토 돌리기'](../../README.md#2-내-사본에서-주간-검토-돌리기) 1~3단계를 따르되, 3단계의 설치 명령에서 `friction-loop` 대신 `ask-expert`를 쓴다. 같은 저장소의 [friction-loop](../friction-loop/README.md)(불편했던 순간을 모아 확장을 고치자고 제안하는 플러그인)를 함께 쓰면, 자문 방식을 고치라는 말이 쌓일 때 `/friction-loop:improve`가 내 사본의 이 파일을 고치자고 제안한다.

## 판단 기준의 근거

아키텍트의 일하는 원칙과 렌즈는 소프트웨어 아키텍트 역량지도, 프론트엔드·웹 플랫폼 아키텍트 역량 매트릭스, AI 에이전트 시스템 아키텍트 역량 매트릭스를 줄여 만들었다. 셋 다 개인 조사 문서라 저장소에 넣지 않았다. 렌즈에는 바뀔 수 있는 수치(성능 지표의 기준값, 접근성 기준 번호, 버전)를 적지 않고 원문 링크만 두어, 아키텍트가 답할 때 원문으로 확인하게 했다.

## 확인한 범위

2026-11-19 기준이다.

- `claude plugin validate --strict`를 통과했다. 다만 이 검사는 agent의 `effort` 값을 확인하지 않는다(엉터리 값도 통과한다). `xhigh`가 실제로 적용되는지는 따로 확인하지 않았다.
- 렌즈의 원문 링크 71개는 2026-11-17에 모두 열리는 것을 확인했다.
- eval 6개 케이스를 플러그인을 켠 쪽과 끈 쪽으로 돌렸다. 마지막 측정에서 켠 쪽은 모두 통과했다. 끈 쪽과 점수 차이가 난 것은 두 케이스다.
  - `state-location`: 켬 5번 중 4번 통과, 끔 5번 모두 실패. 떨어진 1번은 작은 Q의 선택지에 포기하는 것을 빠뜨렸고, 그 규칙을 분명히 적은 뒤 3번 다시 돌려 모두 통과했다.
  - `proactive-bridge`: 켠 쪽만 브릿지 규격을 번호 결정으로 묻고 구현을 멈췄다.
  - 나머지 넷(가설 반박, 위험 찾기, 가벼운 결정, 사실 확인)은 끈 쪽도 통과했다. 플러그인 없이도 Opus가 가설을 반박하고 심어 둔 위험을 찾았다. 이 넷은 차이를 가리지 못하므로 회귀 확인용으로 둔다. 위험 찾기는 켠 쪽이 더 많은 위험을 더 깊게 짚었지만, 비용은 20배가 넘었다.
- eval 안에서는 아키텍트가 웹 문서를 열 수 없어서, 바뀔 수 있는 사실(프레임워크 동작 등)은 아는 지식으로 답하고 "확인 못 함"으로 표시했다. 실제 세션에서 웹 검색을 허용하면 결과가 달라질 수 있다.
- 아키텍트 하나에 렌즈를 싣는 지금 구성이 분야별로 나눈 전문가 여럿보다 나은지는 추론으로 정했다. 비교 실험 계획은 [`evals/README.md`](evals/README.md)의 '다음 실험'에 있다.
